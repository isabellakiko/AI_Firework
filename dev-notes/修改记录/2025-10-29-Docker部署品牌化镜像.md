## 修改背景

### 问题描述

前期已完成前端品牌化定制（侧边栏 + 发送框），但在 Docker 部署（http://localhost:80）中，看到的仍然是官方的 1.8.0 版本样式，没有品牌化效果。

### 原因分析

Docker Compose 配置使用的是官方预构建镜像 `langgenius/dify-web:1.8.0`，该镜像不包含本地的品牌化修改。

**关键理解**：
- Docker 镜像包含的是**编译后的静态文件**，不是源代码
- 本地源代码修改不会自动反映到 Docker 部署中
- 必须重新构建镜像才能让 Docker 看到修改

---

## 解决方案

构建包含品牌化修改的自定义 Docker 镜像，并配置 Docker Compose 使用该镜像。

## 技术要点

### Next.js 构建机制

**关键理解**：
- Next.js 是**构建时渲染**（Build-time rendering）
- 所有样式（CSS、Tailwind、inline styles）在**构建时处理**
- 构建产物：编译后的静态文件（`.next/standalone`、`.next/static`）

**这意味着**：
- ❌ 修改源代码不会自动影响 Docker 部署
- ✅ 必须重新构建镜像才能看到修改
- ✅ 即使只是改颜色/CSS 也需要重新构建

### Docker 镜像构建流程

```
源代码修改
  ↓
Next.js 构建（pnpm build:docker）
  ↓
生成编译后的静态文件
  ↓
打包进 Docker 镜像
  ↓
Docker 容器运行编译后的代码
```

### 为什么样式修改也需要重新构建？

| 修改类型 | 是否需要重新构建 | 原因 |
|---------|-----------------|------|
| CSS 变量 | ✅ 是 | CSS 文件需要编译打包 |
| Inline styles | ✅ 是 | JSX 编译到 JavaScript bundle |
| Tailwind classes | ✅ 是 | Tailwind 需要扫描生成 CSS |
| JSX 属性 | ✅ 是 | React 组件需要重新编译 |

## 经验总结

### 关键收获

1. **理解 Docker 镜像本质**
   - Docker 镜像是编译后的静态文件，不是源代码
   - 源代码修改必须重新构建镜像才能生效

2. **理解 Next.js 构建机制**
   - Next.js 是构建时渲染
   - 样式修改也需要重新构建
   - 构建时处理 CSS、Tailwind、inline styles

3. **掌握开发部署流程**
   - 开发阶段用 `pnpm dev`（实时热更新）
   - 部署测试用 Docker（真实环境）
   - 两者分工明确，效率最高

4. **镜像标签管理**
   - 使用自定义标签（`brand-customization`）
   - 避免与官方版本（`1.8.0`）混淆
   - 便于管理和回滚
