# 前端修改后重新部署指南

## 📖 文档用途

本指南说明**修改前端代码后，如何让 Docker 部署也能看到修改**。

**适用场景**：
- 修改了前端样式（CSS、颜色、布局等）
- 修改了前端组件（JSX、TSX）
- 修改了 Tailwind 类
- 任何前端源代码的修改

---

## ⚠️ 首次部署 vs 后续部署

### 首次部署（从 Git 克隆后）

如果你是**首次从 Git 克隆项目**并准备部署，必须先构建自定义镜像：

```bash
# 在项目根目录执行
docker build -t langgenius/dify-web:brand-customization ./web

# 然后启动服务
cd docker
docker compose up -d
```

**为什么？**
- `langgenius/dify-web:brand-customization` 是本地自定义镜像
- Git 只包含源代码和 Dockerfile，不包含镜像本身
- 必须先构建才能使用

**如果跳过构建直接运行 `docker compose up -d`，会报错：**
```
Error: manifest for langgenius/dify-web:brand-customization not found
```

详细说明：`部署问题排查/2025-11-03-品牌化镜像不存在错误.md`

### 后续部署（修改代码后）

如果你已经部署过，现在是**修改了前端代码**后需要重新部署：

```bash
# 重新构建镜像
docker build -t langgenius/dify-web:brand-customization ./web

# 强制重建容器
cd docker
docker compose up -d --force-recreate web
```

**注意**：必须使用 `--force-recreate`，不要只用 `restart`。

---

## 🔑 核心概念

### 为什么需要重新部署？

**关键理解**：
- Docker 使用的是**编译后的静态文件**，不是源代码
- 本地源代码修改不会自动影响 Docker 部署
- 必须重新构建 Docker 镜像才能看到修改

### 两种环境对比

| 环境 | 代码来源 | 访问地址 | 是否热更新 | 适用场景 |
|------|----------|----------|-----------|----------|
| **本地开发** | 源代码（实时） | http://localhost:3000 | ✅ 是 | 日常开发 |
| **Docker 部署** | 编译后的镜像 | http://localhost:80 | ❌ 否 | 部署测试 |

## 🚀 快速操作指南

### 标准流程（推荐）

每次修改前端代码后：

```bash
# 第 1 步：确认修改已提交到 Git
git add .
git commit -m "描述你的修改"

# 第 2 步：重新构建 Docker 镜像
docker build -t langgenius/dify-web:brand-customization ./web

# 第 3 步：重启容器
cd docker
docker compose restart web

# 第 4 步：验证效果
# 打开浏览器访问 http://localhost:80
```

**预计时间**：5-10 分钟（主要是构建时间）

## 🛠 进阶操作

### 使用不同的镜像标签

**为什么需要？**
- 区分不同版本的修改
- 便于回滚和测试
- 避免混淆

**示例**：

```bash
# 使用语义化版本号
docker build -t langgenius/dify-web:brand-v1.0.0 ./web
docker build -t langgenius/dify-web:brand-v1.1.0 ./web

# 使用功能描述
docker build -t langgenius/dify-web:yellow-buttons ./web
docker build -t langgenius/dify-web:dark-sidebar ./web

# 使用日期
docker build -t langgenius/dify-web:2025-10-28 ./web
```

然后修改 `docker-compose.yaml`：
```yaml
web:
  image: langgenius/dify-web:brand-v1.1.0  # 使用具体版本
```

### 恢复到官方镜像

如果需要暂时恢复到官方版本：

```bash
# 1. 修改 docker-compose.yaml
# 将第 659 行改为：
# image: langgenius/dify-web:1.8.0

# 2. 重启容器
cd docker
docker compose restart web
```

### 同时运行两个版本

```bash
# 官方版本：http://localhost:80
cd docker
docker compose up -d

# 开发版本：http://localhost:3000
cd ../web
pnpm dev
```

这样可以对比测试。

## 🚨 常见问题

### Q1: 构建很慢怎么办？

**A**: 正常情况，首次构建需要 5-10 分钟

**优化建议**：
- 使用国内镜像源（已配置）
- 确保网络稳定
- 关闭不必要的应用释放资源

### Q2: 构建失败了怎么办？

**A**: 检查以下几点

```bash
# 1. 查看详细错误信息
docker build -t langgenius/dify-web:brand-customization ./web

# 2. 确认 Git 状态正常
git status

# 3. 确认依赖安装正常
cd web
pnpm install

# 4. 确认本地构建正常
pnpm build
```

### Q3: 重启容器后看不到修改？

**A**: 可能的原因

1. **浏览器缓存**
   - 解决：强制刷新（Cmd+Shift+R）

2. **没有重新构建镜像**
   - 解决：确认执行了 `docker build`

3. **docker-compose.yaml 没有修改**
   - 解决：确认镜像标签是 `brand-customization`

4. **使用了错误的端口**
   - 解决：确认访问 http://localhost:80（不是 3000）

### Q4: 修改后要等多久？

**A**: 时间分解

| 步骤 | 时间 |
|------|------|
| Git 提交 | ~5 秒 |
| 构建镜像 | 5-10 分钟 |
| 重启容器 | ~10 秒 |
| **总计** | **6-11 分钟** |

**对比本地开发**：
- `pnpm dev`：立即看到修改（热更新）

**建议**：日常开发用 `pnpm dev`，部署测试时才构建 Docker。

### Q5: 可以加速构建吗？

**A**: 几个技巧

1. **使用 Docker 构建缓存**
   ```bash
   # Docker 会自动使用缓存，无需额外配置
   # 只有修改的部分会重新构建
   ```

2. **仅修改样式时**
   - 由于样式在构建时处理，无法跳过构建
   - 建议继续用 `pnpm dev` 开发

3. **使用 Makefile**
   ```bash
   # 项目根目录已有 Makefile
   make build-web
   ```

## 🎯 最佳实践

### ✅ 推荐做法

1. **日常开发用热更新**
   ```bash
   cd web
   pnpm dev
   ```

2. **定期提交 Git**
   ```bash
   git add .
   git commit -m "具体的修改说明"
   ```

3. **重要节点构建镜像**
   - 完成一个功能后
   - 准备部署前
   - 需要分享时

4. **使用清晰的镜像标签**
   ```bash
   docker build -t langgenius/dify-web:brand-v1.0.0 ./web
   ```

### ❌ 不推荐做法

1. **频繁构建镜像**
   - 每次小修改都构建（太慢）
   - 建议用 `pnpm dev`

2. **不提交 Git 就构建**
   - 可能丢失修改
   - 难以追踪

3. **使用 `latest` 标签**
   ```bash
   # 不推荐
   docker build -t langgenius/dify-web:latest ./web
   # 容易与官方镜像混淆
   ```
